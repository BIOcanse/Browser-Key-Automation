# Actions, recording and replay

The extension owns one shared action library. Each action has a unique numeric `actionId`, a nonunique name, a description and an ordered instruction list. An instruction uses the existing command method, schema version and parameters; optional bindings resolve current tabs/elements, input values or earlier results. There is no separate script engine.

Use `actions.create` to save a sequence directly, `actions.list` to search and page, and `actions.get` to read instruction pages. `actions.compile` previews the normalized sequence and required permissions; it does not execute it. `actions.run` submits one action by ID with its inputs. `actions.update/delete` take the current revision so an old editor cannot overwrite newer work. Parameters and limits are in `commands.registry.json`.

The command and all its action requirements are authorized once before entering the existing Key queue. Later Key expiry, disabling, revocation or permission edits affect new submissions. An accepted action continues under its command deadline; a target failure, explicit stop or App loss remains a real execution failure. Read the returned step results and trace before deciding any recovery.

Revoking a Key deletes its record and stored token. It disappears from Key management and the action manager's Key selector; later get/reveal calls cannot recover it. Disabling remains reversible. Upgrading removes revoked records left by earlier releases.

Start a recording with `recording.start` using a current `tabRef`, scope, mode and maximum duration. `recording.pause/resume/stop` control sampling; `recording.list/read` page through metadata and raw events. Stop before compiling or deleting. Recordings are local and belong to the selected Key.

- `mode: "dom"` records supported interactions as editable DOM operations and locators. Shadow roots and identifiable frames retain their target path. Child history/hash and document navigation compile to `page.wait` with a frame path; later steps resolve the updated child document. Ambiguous frames, unsupported pointer paths and unfinished gestures remain explicit compile diagnostics.
- `mode: "real"` uses the Windows x64 App to observe the selected window. It records visible, unobscured window-relative native pixels, all five mouse buttons (left/right/middle/back/forward), both wheel axes, keyboard keys and window changes. Off-window pointer coordinates are excluded before buffering. Virtual replay does not move the physical cursor.

Pass `{recordingId, options:{timing:"preserve", mergeInputs:"none", includeHover:true}}` as the `instructions` source of `actions.compile` or `actions.create`. The preview contains ordinary window and virtual-input commands. Mouse input uses `{kind:"moveWindow",x,y}` directly, independent of CSS zoom or content-window replacement. Incomplete gestures and legacy screen-coordinate drafts require review or a new recording. Keyboard keys retain scan codes, layout and repeat; this external observer does not record IME committed text.

Before virtual replay, acquire the entire destination window with `control.acquire`. Check the selected tab and page state. `windows.get/setState/setBounds/focus`, `page.viewport.get`, and `page.zoom.set` are explicit observation and correction commands. Prefer `ensure.run` schema 2 for meaningful preconditions and explicit corrections around a recorded sequence. Do not add a reset or activation to every recorded step, and do not retry an unconfirmed submission.

For the broader browser toolset, use `files.*`, `downloads.*` and `dialogs.*` for transfers and page dialogs; `network.*`, `console.*`, `performance.*` and explicit `debugger.*` for diagnostics; registered capture commands for viewport/document/element images; and the registered tab-search, bookmarks and history commands for browser data. Check the generated registry for each exact method rather than expanding wildcard names into guessed commands.

Call `virtualMouse.moveWindow({tabRef,x:240,y:160})` to set the single virtual pointer in native pixels from the outer window top-left. Then `virtualMouse.down/up({tabRef,button:"back"})` or `button:"forward"`, clicks without `at`, and scrolling without `at` use that position. `virtualMouse.get` reports `coordinates:"window"`. An explicit ordinary `move` or CSS `at` changes the pointer back to `css_viewport`. No separate mouse is created.
